# Mode 2: Video Script (Text → Video Storyboard)

把任意输入——长文章（新闻、博客、政策文件）或一句话创意需求——转换成一套完整的、可直接喂给文生视频模型（以 LTX-2 的提示词规范为准）的分镜头脚本。整个过程分五步：理解输入并提炼立意 → 必要时澄清 → 拆分镜头 → 填写 shots.json 并通过校验门 → 渲染输出。

不要把这件事做成"把文章逐句翻译成画面描述"。真正的工作是先想清楚这套视频要讲一件什么事、给人什么感受，再围绕这个核心去设计镜头——文章/一句话只是素材，不是脚本本身。

**写每个镜头提示词之前必须先读 [`references/guides/video-prompt-guidelines.md`](../references/guides/video-prompt-guidelines.md)**——它包含六要素的展开说明、风格术语表、技术标记词表、LTX-2 擅长领域与避免事项、对话格式、完整示例和检查清单，不要凭记忆瞎写术语。

## 速查表

| 步骤            | 输入                        | 输出                                                    | 是否可能停下来等用户          |
| --------------- | --------------------------- | ------------------------------------------------------- | ----------------------------- |
| 1. 提炼立意     | 原始文章/一句话             | 一两句话定下"讲什么事、什么感受"                        | 否                            |
| 2. 判断是否澄清 | 立意 + 原始输入里缺失的信息 | 问卷式问题（风格/篇幅/对话/情绪基调），或确认理解后跳过 | 是，信息不全时                |
| 3. 拆分镜头     | 立意 + 澄清结果             | 镜头大纲（每镜头一句话）+ shots.json 骨架               | 是，大纲是推断/发挥出来的时候 |
| 4. 写提示词     | 镜头大纲                    | shots.json 填全（含英文提示词）并通过校验门             | 否                            |
| 5. 输出         | 校验通过的 shots.json       | 渲染出的固定格式完整脚本                                | 是，输出后请用户反馈          |

## 第一步：判断输入类型，提炼核心立意

先判断输入属于哪一类：

- **长文本**（新闻/博客/政策文件等）：通读全文，提炼出核心事件或论点、关键人物/主体、情绪基调、以及哪些段落天然适合变成画面。不要试图覆盖全文细节——找到文章真正想传达的"一件事"，把它当成故事的骨架。
- **一句话需求**（如"帮我生成一个关于深夜便利店的治愈故事"）：这是创意 brief，需要主动补全细节——主角是谁、发生在哪、情绪走向是什么、结局是什么。

无论哪种输入，最终都要确定：**这套视频要讲一件什么事，给人什么感受**。这是后面所有镜头设计的锚点，简短地写一两句话把它定下来。

## 第二步：判断是否需要向用户澄清

如果以下任意一项无法从输入中合理推断，就问用户，不要替用户瞎做决定：

- **视觉风格**：写实电影感 / 动画(2D、3D、定格、像素) / 风格化(赛博朋克、漫画感、超现实)——参考 `references/guides/video-prompt-guidelines.md` 里的风格分类表
- **篇幅**：大致想要几个镜头（短视频通常 3-6 个；如果输入是一整篇长文章，可能需要更多）
- **是否需要对话/旁白**，以及用什么语言
- **情绪基调**：如果原文立场/情绪本身不明确（比如一篇中性的政策文件），需要问用户希望传达什么情绪——温暖、紧张、严肃、讽刺等

如果输入已经足够具体（比如用户直接写了"做成黑色电影风格的 5 个镜头"），就不要多此一举地问，把你的理解简短复述一遍确认即可，然后直接进入下一步。

提问时优先用问卷式/选择题的方式，而不是开放式提问。一次性问完所有需要澄清的点，不要一个一个来回追问。

## 第三步：拆分镜头（分镜）

确定了立意和风格之后，把内容拆成一系列连续的镜头(shot)。这一步是叙事设计，不是逐字翻译：

- **长文章**：找到文章里 2-6 个最有画面感、最能代表整体立意的节点，每个节点对应一个镜头，不需要面面俱到。
- **一句话需求**：按一个最小可行的叙事弧线展开——通常是"起（建立场景/人物）→ 承（动作展开/转折）→ 合（结果/情绪落点）"，根据需要的篇幅拆成 3-6 个镜头。

先用一两句中文列出镜头大纲，让整体结构先成型，再进入逐镜头的详细提示词写作。如果镜头之间有强烈的视觉/光线连贯性要求（比如同一场雨夜戏），要在大纲阶段就标注清楚，避免后面镜头之间风格打架。

**大纲做完之后，先判断要不要停下来确认，再决定往下走多远：**

- 如果立意/大纲是你主动推断或发挥出来的——先把镜头大纲发给用户，等用户回应"对/改一下"之后再去写详细提示词。大纲方向一旦理解错了，后面整套详细提示词都是白写。
- 如果用户的需求已经很明确具体，可以把大纲和详细提示词一次性给全，不用专门停下来等回复——但大纲依然要在最终输出里清楚地单独列出来。

大纲方向确认之后，把它落成 `shots.json`（与最终脚本存同一工作目录）。它是后续校验与渲染的唯一事实源，字段如下：

```json
{
  "title": "深夜便利店的旧友",
  "logline": "疲惫的店员在雨夜与突然出现的旧友重逢",
  "style": "写实电影感，冷暖光对比",
  "shots": [
    {
      "id": "shot-1",
      "summary": "雨夜便利店全景，店员在补货",
      "seconds": 8,
      "shot_size": "wide shot",
      "camera_motion": "static",
      "dialogue": "无",
      "prompt": ""
    }
  ]
}
```

- `seconds`：镜头时长（秒）。单镜头上限默认 15s，全部镜头加总 ≤60s 的成片降为 12s——装不下就拆镜头，不要让一个镜头装一段戏（上限是拆镜策略口径：LTX-2 官方模型卡未设最大时长，参考配置 121 帧@24fps≈5s 且帧数须 8k+1，15s/12s 均为该约束下可实现时长）
- `camera_motion`：只能填 [`video-prompt-guidelines.md`](../references/guides/video-prompt-guidelines.md) 五节词表里的运镜术语（校验门会查枚举）；选词参考 [`references/guides/camera-movements.md`](../references/guides/camera-movements.md) 的情绪域对照与起承合运镜序列模板，把立意里定的情绪基调直接落到运镜上
- `dialogue`：无台词也必须写，显式填"无"；有台词用 guidelines 八节的 `角色名（情绪/语气）："内容"` 格式
- 长文章改编、镜头多到单次生成装不下时，加 `segments` 数组标记哪些镜头属于同一次生成调用：`"segments": [{"id": "seg-1", "shot_ids": ["shot-1", "shot-2"]}]`；镜头顺序始终以 `shots` 数组为准

## 第四步：逐镜头写提示词

严格遵守 [`references/guides/video-prompt-guidelines.md`](../references/guides/video-prompt-guidelines.md) 里的完整规范。核心要点：

- 每个镜头的提示词是**一段连贯的英文段落**，不要分点罗列
- 用**现在时态**描述动作（walks, turns, pans——不是 walked, turned）
- 大约 **4-8 句话**覆盖全部要素；特写镜头细节要更精确，远景可以粗一些
- 必须自然带出六大要素（镜头设定、场景搭建、动作描述、角色定义、镜头运动、音频/对话），让它们融进一段流畅描述里——风格术语建议前置
- 情绪要靠姿态/手势/表情来表现，不要直接写"sad"、"nervous"这类内心状态词——模型无法直接生成内心状态
- 不要要求画面里出现可读文字、Logo、招牌——模型生成不出清晰一致的文字
- 光源逻辑要自洽，除非有明确动机不要冷暖光混用——冲突光源会生成不自然的画面
- 不要让一个镜头塞进太多动作或太多角色，复杂的物理动作容易出伪影
- 如果某个镜头有台词，用 `角色名（情绪/语气）："内容"` 的格式标注

提示词写进 `shots.json` 各镜头的 `prompt` 字段。全部填完后，对照 `references/guides/video-prompt-guidelines.md` 末尾的检查清单过一遍，然后跑交付校验门：

```bash
# {SKILL_DIR} 为本 skill 的安装目录（如 ~/.zcode/skills/cangjie），脚本纯标准库，无需安装依赖
python3 {SKILL_DIR}/scripts/validate_video_script.py <shots.json 路径>
```

FAIL 必须逐条修到 0 才能进第五步——每条消息都指到具体镜头和原因，按消息修 `shots.json` 后重跑；WARN 是建议项，逐条判断后可保留。门结果会自动累积到 shots.json 同目录的 `.gates.jsonl`，不需要手工维护。

## 第五步：输出格式

校验门 0 FAIL 之后，把 `shots.json` 渲染成下面的格式。渲染是机械映射：标题/立意/风格取自顶层字段，镜头数取 `shots` 数组长度，每个镜头的标题行取 `summary`、正文取 `prompt`——不要在渲染时改写内容，发现要改就回 `shots.json` 改完重新校验。

```
## [脚本标题]

**立意**：一句话说明这套视频想表达什么
**风格**：视觉风格 + 整体基调
**镜头数**：N 个

---

### Shot 1 — [一句话场景概括]
[完整的英文提示词段落]

### Shot 2 — [一句话场景概括]
[完整的英文提示词段落]

...
```

提示词本身用英文写（文生视频模型对英文提示词的理解和效果普遍更好），但脚本标题、立意说明、场景概括这些给用户看的部分用中文。如果用户明确要求提示词也用中文或其他语言，跟随用户的要求。

写完之后，简短地问用户对整体方向、镜头数量、或某个具体镜头是否满意——这是个创意协作的过程，预期会有几轮来回调整。来回调整的过程**不跑校验门**，门只对最终交付产物负责：调整时只改 `shots.json` 里对应镜头的字段，定稿交付前再跑一次校验、确认仍然 0 FAIL 即可，避免每轮迭代都被门打断。

## 边界情况速查

| 情况 | 处理方式 |
| ---- | ------- |
| 输入只是一个抽象主题词（如"等待"、"重逢"），没有更多上下文 | 当成一句话需求，主动构建一个最小叙事，给出合理解读再让用户在大纲确认环节调整方向，而不是抛一堆开放式问题卡住流程 |
| 输入是非中文 | 工作流不变；和用户的沟通跟随输入语言走；提示词本身依然写成英文 |
| 用户要的视觉风格不在风格表里（如"国风"、"水墨风"） | 不要硬套表格现成词，也别退回"cinematic"敷衍——按风格本身的视觉特征（光线、色彩、质感、构图）具体描述 |
| 输入信息少到连最小叙事都立不住 | 不要凭空编一整套脚本，回到第二步直接问：是想做成小故事、氛围片段、还是别的 |
| 用户对某一个镜头不满意要求修改 | 只重写被指出的镜头（改 `shots.json` 对应字段），不要把整套脚本推倒重来；如改动影响其他镜头连贯性，提醒用户一句但不擅自连带改；交付前重跑一次校验门 |
| 镜头里有台词但用户没说明语言 | 默认跟输入语言保持一致，不要不声不响切成英文 |
